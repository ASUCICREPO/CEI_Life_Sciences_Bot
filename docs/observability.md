# Operations and observability

The CDK stack configures X-Ray on the REST API, application Lambdas, and AgentCore runtime trace delivery. AgentCore Python packages include AWS OpenTelemetry and initialize its instrumentation before importing application code. Initialization happens in Python because cross-platform CodeZip builds can otherwise include a host-specific executable. Generic HTTP-client auto-instrumentation is disabled because URLs may contain queries or API keys; AWS SDK instrumentation remains enabled. ADOT's GenAI extraction stays enabled and its OTLP log exporter is disabled: recognized model content is removed from exported spans and the extracted log events are discarded. This does not guarantee that all sensitive data is excluded from other span fields; inspect real traces after deployment. Lambda trace sampling still applies. The Runner and Agent Proxy pass Lambda trace context to AgentCore; verify the resulting service map and trace linkage after deployment. These settings alone do not prove that every internal model or tool call has an instrumented span.

CloudWatch Transaction Search is an account/Region-level setting, not enabled by this stack. It is required for the AgentCore generative AI observability views and trace delivery. On 9 November 2026, `cei-project` in `us-east-1` was configured with the CloudWatch Logs resource policy `cei-transaction-search-xray`, the `CloudWatchLogs` trace destination, and a 1% indexing rule. Verify readiness with `aws xray get-trace-segment-destination --profile cei-project --region us-east-1`; the destination must report `ACTIVE` before deploying. For other accounts or Regions, follow the [AWS setup instructions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.html). This setting affects the account and Region, not just this application. AgentCore instrumentation and model-content opt-out must be verified with real traces before assuming their behavior.

## Alerts

The stack creates `cei-life-sciences-alerts` and subscribes the configured `adminEmail`. The recipient must confirm the SNS subscription email before notifications are delivered. Alarm messages contain resource and metric information, not request bodies. The topic is not encrypted at rest: AWS requires a customer-managed KMS key for CloudWatch to publish to an encrypted SNS topic, while decision B52 excludes customer-managed keys. SNS enforces HTTPS.

Initial thresholds are deliberately sensitive and should be tuned against observed production traffic:

- API Gateway 5xx rate: 5% over five minutes.
- Application Lambda errors and throttles: one in five minutes per function and metric.
- DynamoDB throttles: one in five minutes, aggregated by operation per table. Partial batch throttles also appear in read/write throttle event metrics and should be reviewed separately.
- Handled failures: one in five minutes for the Runner, Router, session APIs, Exports, UI actions (`resume_failed`), Jobs (including `runtime_stop_failed`), Agent Proxy, NCBI read-only, token refresh, and each data-source function. These include partial openFDA failures, failed CMS detail fetches, Runner stream transport failures, and replay timeouts.
- Browser failures: five authenticated diagnostic reports in five minutes.
- Sign-up attempts: 20 in five minutes; Gateway policy denials: 5 in five minutes.
- CloudFront WAF: 25% blocked out of at least 100 allowed or blocked requests in five minutes. Its alarm runs in `us-east-1` and targets the shared topic in the application Region.

The CloudWatch dashboard is named `BackendStack-operations` for the normal stack. It includes a count of agent application errors returned with HTTP 200; this is a dashboard signal without an agent-health alarm, in line with B75. A lack of metric data does not prove that delivery is working. The application-level metrics depend on log ingestion; the Gateway denial metric depends on the Gateway emitting a `DENY` decision. Guardrails are not deployed, so a guardrail-intervention alarm is not configured. Internal AgentCore model/tool spans are not comprehensively covered by these alarms.

Authenticated browser clients report fixed failure categories, HTTP status codes, and optional validated API request IDs to `POST /client-diagnostics`. The endpoint rejects extra fields and does not record user IDs, prompts, URLs, error text, tokens, or response bodies. Its CloudWatch log group retains records for one month. The browser keeps at most ten reports in memory, retries buffered reports when it comes back online, and clears them on sign-out or page teardown. Failures before authentication, failures while the diagnostic endpoint remains unreachable, and queued reports lost when a page closes cannot be reported.

## Investigating a request

1. Search the API access log group for the response's `request_id`. Its route, status, and time identify the entry point. For `/chat/stream`, search `SessionRunnerLogs` for the same ID; `stage` and `outcome` identify where the Runner failed.
2. Search `SessionRouterLogs` for that request ID. Its `stage`, `error_type`, AWS error code when available, and, for token endpoint HTTP errors, status are logged without token or request contents. Lambda request IDs and timestamps can link invocations when an API request ID is unavailable. Session REST exception logs retain exception types and source locations but omit exception messages.
3. Inspect the corresponding AgentCore runtime log group and the X-Ray trace. Traces may be absent because of sampling, configuration, or delivery failure; absence is not evidence that the runtime was not called.
4. Check the dashboard and alarm history, then inspect the specific source Lambda or Gateway logs for an upstream failure or policy decision. `agent_proxy_application_error` identifies an HTTP 200 carrying an application error without recording its body. Pipeline job failures remain visible in the job view, as required by B75. Avoid copying prompts, tokens, or user data into incident notes.

For the 9 November 2026 `/chat/stream` 502, API Gateway reported a missing delimiter. The Runner previously ended early error responses with `end(body)` without first calling `write()`. In the [Lambda Node runtime](https://github.com/aws/aws-lambda-nodejs-runtime-interface-client/blob/main/src/HttpResponseStream.js), the HTTP metadata and delimiter are emitted on the first write, so that path can produce the observed 502. The Runner now writes before ending and sends an initial SSE comment to establish the stream framing. The underlying error that led to the original early response is still unknown; the new stage and error-type logs are intended to identify it on recurrence.

## Deployment verification

After a deployment to a non-production environment, confirm the email subscription, invoke a safe test request, verify the API/Lambda/AgentCore trace chain, and exercise a controlled handled failure and alarm transition. Confirm an email arrives and check the WAF alarm's cross-region SNS action when the backend Region differs from `us-east-1`. These live checks are necessary: CDK synthesis and unit tests cannot prove trace delivery, SNS delivery, or the exact contents of service-generated Gateway logs.
