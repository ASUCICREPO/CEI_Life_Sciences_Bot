## What the AWS docs already say (read 2026-10-06, not yet proven on a deployed Gateway)

These change how the spec examples in `auth-and-tool-scope.md` section 6 must be written. The docs are at `https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/` (`policy-scope.md`, `policy-conditions.md`, `policy-understanding-cedar.md`, `policy-permissions.md`, `policy-enforcement-modes.md`, `example-policies-principal.md`).

- Cedar is default deny already. A blanket `forbid(principal, action, resource);` is an emergency shutdown that overrides every permit. The spec's "default deny" example must not be deployed. The spike writes permits only.
- Cedar has no wildcard in action names, so `action like GatewayAction::"pubmed___*"` is invalid. The documented way to get one permit per target is `action in AgentCore::Action::"<TargetName>"` (the target is an action group). A policy that names an action needs `resource == AgentCore::Gateway::"<gateway-arn>"`.
- The principal is `AgentCore::OAuthUser`. JWT claims are string tags. The Cognito `scope` claim is one space-separated string, so the permit is `principal.hasTag("scope") && principal.getTag("scope") like "*cei-tools-spike/target-a*"`. Use `hasTag` before `getTag`; reading a missing tag denies the request.
- `initialize` and `tools/list` are not Cedar actions in the generated schema (only `<Target>___<tool>` actions exist, all under `CallTool`). The spike therefore has no permit for them. `tools/list` filtering is done by the Gateway through the `bedrock-agentcore:PartiallyAuthorizeActions` permission on the Gateway role. The spec's "permit initialize/tools/list" statement cannot be written.
- Mode is on the Gateway, not the engine: `CfnGateway.policyEngineConfiguration = { arn, mode: LOG_ONLY | ENFORCE }`. `CfnPolicy.enforcementMode` (`ACTIVE` | `LOG_ONLY`) is a second, per-policy switch; the spike leaves it at `ACTIVE`. `bedrock-agentcore:UpdateGateway` can flip `ENFORCE` to `LOG_ONLY` or remove the engine, so F4 must guard it.
- The Gateway role needs `GetPolicyEngine`, `AuthorizeAction`, `PartiallyAuthorizeActions`. Without them every call is denied and attaching the engine can fail with `InternalServerException`.
- `CreatePolicy` validates actions against the Gateway tool schema, so each policy depends on its target. The deploying role needs `bedrock-agentcore:InvokeGateway`. Engine and policy names are `[A-Za-z][A-Za-z0-9_]*` (no hyphens).

Open points to confirm on the deployed run: target names in `CfnGatewayTarget.name` are exactly the Cedar action group names; `CfnPolicy.definition.cedar` is accepted (the API docs show `policy`); the LOG_ONLY deny log format (the script does a best-effort match and reports `WARN` if it finds none).

Confirmed on 2026-10-28: the stack deployed and the per-target permits allowed exactly their targets, so `CfnGatewayTarget.name` does work as the Cedar action group name and `CfnPolicy.definition.cedar` was accepted. The LOG_ONLY log format is still unconfirmed (LOG_ONLY pass not run).

## Question 1: does Cedar `like` match as a substring?

- Test: `s2_scope_test.py`, task 1 checks (scope claim is one space-separated string) and the ENFORCE rows for `a_only`, `a_shared`, `all`. The permit uses `like "*cei-tools-spike/target-a*"`, so a pass proves wildcard matching on the whole claim string.
- Limit: a true collision test needs a scope whose name contains another one. The stack avoids that on purpose (B69), so the deployed run cannot show a false positive. The docs state `*insurance:claim*` also matches `insurance:claim:admin`.
- Result: **PASS** (2026-10-28). `a_only`, `a_shared` and `all` tokens (scope claim is one space-separated string, confirmed in task 1) were allowed on target A; `b_only` and `none` were denied. The `like "*cei-tools-spike/target-a*"` permit matched inside a multi-scope claim. The collision case stays unproven by design (see Limit), so F4 must still follow the B69 no-substring naming rule.

## Question 2: does `tools/list` filtering by scope work on the GA Policy engine?

- Test: ENFORCE run, `[a_only] tools/list shows only its tools` expects exactly `SpikeTargetA___echo` and `SpikeTargetShared___echo`; `[none]` expects only the shared tool. Raw responses are in the JSON under `raw.tools_list_*`.
- Result: **PASS** (2026-10-28). Every token's `tools/list` returned exactly its permitted tools: `a_only` → A + shared, `b_only` → B + shared, `a_shared` → A + shared, `none` → shared only, `all` → A + B + shared. Filtering is done Policy-side by the Gateway with no Cedar permit for `tools/list`, as the docs said. F4 can rely on Policy-side filtering alone; no client-side filter is needed.

## Question 3: can the runtime role be kept from reading the M2M secret?

- Test: script section `secret`. The runner role reads the secret; the runtime role (which has an over-broad `secretsmanager:GetSecretValue` on `*` on purpose) and the CloudShell caller get `AccessDeniedException` from the secret's explicit resource-policy Deny (`aws:PrincipalArn` is not the runner role). Jest also checks the policy shape offline.
- Result: **PASS** (2026-10-28). Runner role read the secret. Runtime role got `AccessDeniedException` despite its `GetSecretValue` on `*`. The caller got `AccessDeniedException` even though it is an IAM user with `AdministratorAccess`, so the resource-policy Deny holds against admins too. The pattern works for F4's real Router.

## Question 4: what does a denied Gateway call look like inside LangGraph?

- Test: ENFORCE run, task 8. `fake_langgraph_node` calls `SpikeTargetB___echo` with the `a_only` token and stores `exception_type`, `http_status`, `jsonrpc_error`, `is_error_result` and the raw body under `raw.deny_shape` (the Gateway runs with `exceptionLevel: DEBUG`).
- Result: **characterized** (2026-10-28). A policy deny is **HTTP 200** with a JSON-RPC error, not an HTTP error and not an MCP `isError` tool result:
  ```json
  {"jsonrpc":"2.0","id":22,"error":{"code":-32002,"message":"Tool Execution Denied: Tool call not allowed due to policy enforcement [No policy applies to the request (denied by default).]"}}
  ```
  `exception_type` in the fake node: `GatewayCallError`; `is_error_result: false`.
- Consequence for F4/F5: agent code cannot detect a deny from the HTTP status. It must read the JSON-RPC `error.code` (`-32002` = policy deny). It must also tell a deny apart from a protocol error (`-32600`, see the summary) and an expired token (HTTP 403, question 5); the first, invalid run shows how easily those get confused.
- The agent's response to a deny (retry, tell the user, fail the turn) is still an F4/F5 decision and needs user approval.

## Question 5: does the B67 token-refresh pattern work end to end?

- Test: task 9. The runtime role signs (SigV4) a POST to the IAM-authenticated Function URL with an old token and `run_id`; expects HTTP 200, same scope set, a different token that works at the Gateway (and stays denied for B under ENFORCE). `run_id=inactive` must return 409, an unsigned call 403. With `--wait-expiry` the script waits for the 5-minute TTL, expects HTTP 401 from the Gateway for the expired token, then a working token after refresh.
- The stub runs as the runner role (the only identity allowed to read the secret). It reads the scopes from the caller's token without checking the signature; the real endpoint must take the scopes from the run record.
- Result: **PASS with one caveat** (2026-10-28). The SigV4-signed refresh returned HTTP 200, the same scope set, and a different token; the new token called A and stayed denied on B. `run_id=inactive` got 409 and an unsigned call got 403. After the 5-minute TTL the old token was rejected, and a refresh after expiry returned a working token.
- Caveat: the expired token was rejected with **HTTP 403, not 401** (the only FAIL in the run). F4/F5 refresh logic must treat a Gateway 403 as possibly "token expired, refresh and retry once", not only a 401. Whether a 403 is ever also returned for other reasons (it would then need to be told apart from an expiry) was not tested.
