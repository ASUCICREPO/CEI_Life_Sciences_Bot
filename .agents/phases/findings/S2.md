## How to run

The spike stack is `ToolScopeSpikeStack` (B92). All builds run in CodeBuild (B91).

1. Normal deploy first (unchanged): `./deploy.sh`.
2. Deploy with the spike in `LOG_ONLY`: `./deploy.sh --spike tool-scope` (same as `--spike-policy-mode LOG_ONLY`).
3. In CloudShell, from `backend/scripts/spikes/`: `python3 s2_scope_test.py --out s2-log-only.json`. CloudShell credentials need `sts:AssumeRole` on the two spike roles and `cloudformation:DescribeStacks`.
4. Flip to `ENFORCE`: `./deploy.sh --spike tool-scope --spike-policy-mode ENFORCE`. This is an in-place Gateway update, no replacement.
5. Run the script again: `python3 s2_scope_test.py --wait-expiry --out s2-enforce.json`.
6. Keep both JSON files, fill in the results below, then destroy: `aws cloudformation delete-stack --stack-name ToolScopeSpikeStack` (a later `deploy.sh` without `--spike` does not remove it).
7. Remove the hooks marked `FIXME: remove after S2 validation (B92)` in `backend/lib/app.ts`, `deploy.sh`, `buildspec.yml`, and delete the spike files.

## What the AWS docs already say (read 2026-10-06, not yet proven on a deployed Gateway)

These change how the spec examples in `auth-and-tool-scope.md` section 6 must be written. The docs are at `https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/` (`policy-scope.md`, `policy-conditions.md`, `policy-understanding-cedar.md`, `policy-permissions.md`, `policy-enforcement-modes.md`, `example-policies-principal.md`).

- Cedar is default deny already. A blanket `forbid(principal, action, resource);` is an emergency shutdown that overrides every permit. The spec's "default deny" example must not be deployed. The spike writes permits only.
- Cedar has no wildcard in action names, so `action like GatewayAction::"pubmed___*"` is invalid. The documented way to get one permit per target is `action in AgentCore::Action::"<TargetName>"` (the target is an action group). A policy that names an action needs `resource == AgentCore::Gateway::"<gateway-arn>"`.
- The principal is `AgentCore::OAuthUser`. JWT claims are string tags. The Cognito `scope` claim is one space-separated string, so the permit is `principal.hasTag("scope") && principal.getTag("scope") like "*cei-tools-spike/target-a*"`. Use `hasTag` before `getTag`; reading a missing tag denies the request.
- `initialize` and `tools/list` are not Cedar actions in the generated schema (only `<Target>___<tool>` actions exist, all under `CallTool`). The spike therefore has no permit for them. `tools/list` filtering is done by the Gateway through the `bedrock-agentcore:PartiallyAuthorizeActions` permission on the Gateway role. The spec's "permit initialize/tools/list" statement cannot be written.
- Mode is on the Gateway, not the engine: `CfnGateway.policyEngineConfiguration = { arn, mode: LOG_ONLY | ENFORCE }`. `CfnPolicy.enforcementMode` (`ACTIVE` | `LOG_ONLY`) is a second, per-policy switch; the spike leaves it at `ACTIVE`. `bedrock-agentcore:UpdateGateway` can flip `ENFORCE` to `LOG_ONLY` or remove the engine, so F4 must guard it.
- The Gateway role needs `GetPolicyEngine`, `AuthorizeAction`, `PartiallyAuthorizeActions`. Without them every call is denied and attaching the engine can fail with `InternalServerException`.
- `CreatePolicy` validates actions against the Gateway tool schema, so each policy depends on its target. The deploying role needs `bedrock-agentcore:InvokeGateway`. Engine and policy names are `[A-Za-z][A-Za-z0-9_]*` (no hyphens).

Open points to confirm on the deployed run: target names in `CfnGatewayTarget.name` are exactly the Cedar action group names; `CfnPolicy.definition.cedar` is accepted (the API docs show `policy`); the LOG_ONLY deny log format (the script does a best-effort match and reports `WARN` if it finds none).
